OS PBL class · Task 1: Spacecraft Communication System

PriorityLink

Making sure the most critical message always gets through. A priority-based communication system built on FreeRTOS.

Try the idea How it works GitHub repository

The problem

During a docking maneuver, a spacecraft receives a flood of routine telemetry just as a critical fault alarm arrives. The alarm must not wait behind the data.

Limits of existing approaches

Generic messaging treats all traffic alike, so urgent messages can be delayed or lost under load, putting crew and mission at risk.

Core issue

  • Urgent alarms can be delayed or lost under load
  • Routine telemetry competes for the same resources
  • The operating system decides who gets through

Our solution

PriorityLink ranks every message by urgency and lets the operating system make sure the important ones go first.

1. Ingest

  • Emergency, System and Normal sources
  • Each stream has its own priority
  • Payloads encrypted before sending

2. Deliver reliably

  • Priority-based task scheduling
  • Queues absorb traffic bursts
  • Automatic retry with backoff

3. Monitor and trace

  • Timestamped log of every event
  • Live queue and backlog view
  • Failure reports for audits

Message types

TypeExamplePriorityProcessing rule
EmergencyFault alarm, abort commandHighProcessed first, immediate retry
SystemSubsystem status and healthMediumProcessed after Emergency messages
NormalRoutine telemetry, general messagesLowProcessed when the CPU is free; may wait in the queue

How it works

Senders put messages into one queue per priority. The receiver always takes the most urgent one first. Failed deliveries are retried with backoff, and every step is logged.

Retry and Backoff Task

The sender encrypts the payload with XOR and adds a checksum before queueing; the receiver verifies the checksum, then decrypts. Normal messages are only delayed under overload, never dropped. Every step is logged.

Scheduling

Task priorities decide which task runs first.

IPC

Queues carry messages between tasks.

Synchronization

No lost or corrupted data.

Key decisions

Queues

One queue per priority, 16 messages each, 32-byte payloads. Normal messages are delayed under overload, never dropped.

Retry

Up to 3 retries, waiting 10, 20 and 40 ms. Emergency messages are retried immediately. A message that still fails is logged.

Security and testing

Encrypt, then checksum, at the sender; verify, then decrypt, at the receiver. Failures are simulated with a random drop at the receiver.

Goals and scope

Technical goals

  • Emergency first in 100% of test runs
  • 99%+ delivered within 3 retries
  • 100% of failures logged

Learning goals

  • Understand scheduling and IPC in a real RTOS
  • Explain design limits and trade-offs
  • Practice teamwork and documentation

Constraints

  • FreeRTOS on the Windows MSVC simulator, no real hardware
  • Simulated messages and link, no real radio
  • XOR is a demo cipher, not flight-grade security
